\noindent
Die Anwendung unterst\"utzt Fachinformatiker-Azubis beim Führen ihrer
w\"ochentlichen Ausbildungsnachweise. Stichworte werden links eingetragen, eine
\emph{lokale} Sprachmodell-Engine strukturiert sie thematisch, und rechts
erscheint das daraus erzeugte PDF.

\section{Hintergrund \& Aufbau}

Die App ist in Python mit \textbf{PySide6} (Qt~6) umgesetzt und in klar getrennte
Module gegliedert:

\begin{itemize}
  \item \texttt{ihk\_nachweise/app.py} -- Anwendungseinstieg (Qt-Setup).
  \item \texttt{ihk\_nachweise/main\_window.py} -- Orchestrierung von Eingabe,
        LLM, PDF-Erzeugung und Anzeige.
  \item \texttt{ihk\_nachweise/widgets/} -- Oberfl\"ache: Metadaten-Leiste (oben),
        Eingabe-Panel (links), PDF-Anzeige via \texttt{QPdfView} (rechts).
  \item \texttt{ihk\_nachweise/llm/} -- Modellkatalog, Download- und
        Generierungs-Worker.
  \item \texttt{ihk\_nachweise/pdf/} -- PDF-Erzeugung mit \textbf{reportlab}.
  \item \texttt{ihk\_nachweise/storage/} -- Rohdaten als \texttt{.txt}
        (verlustfrei wieder einlesbar).
  \item \texttt{ihk\_nachweise/config.py}, \texttt{paths.py} -- Konfiguration
        (JSON) und plattform\"ubliche Speicherorte.
\end{itemize}

\noindent
Langlaufende Aufgaben (Modell-Download, Textgenerierung) laufen in eigenen
Qt-Threads, damit die Oberfl\"ache bedienbar bleibt.

\section{Lokale LLM}

Die Sprachverarbeitung erfolgt \textbf{vollst\"andig lokal} -- es werden keine
Daten an einen Online-Dienst gesendet.

\begin{itemize}
  \item \textbf{Engine:} \texttt{llama-cpp-python} (nutzt Metal auf macOS, CPU
        unter Windows). Die nativen Bibliotheken sind im Paket enthalten.
  \item \textbf{Modelle:} GGUF-Dateien von Hugging Face. Ausw\"ahlbar u.\,a.
        \emph{Qwen2.5 3B} (Standard, ca.\ 1{,}9\,GB), \emph{Llama 3.2 3B},
        \emph{Qwen2.5 7B} sowie \emph{Qwen2.5 1.5B}.
  \item \textbf{Download bei Bedarf:} Das gew\"ahlte Modell wird beim ersten
        Verwenden automatisch heruntergeladen (mit Fortschrittsanzeige) und
        danach wiederverwendet. Es ist \emph{nicht} im Installationspaket
        enthalten.
  \item \textbf{Strukturierung:} Aus den Stichworten werden wenige thematische
        Oberkategorien mit \"Uberschriften und Stichpunkten gebildet.
  \item \textbf{Neu generieren:} Erzeugt das Ergebnis mit mehr Variation neu und
        \"uberschreibt die vorige Fassung.
\end{itemize}

\section{Installation \& Distribution}

\subsection*{Entwicklung (aus dem Quellcode)}
\begin{verbatim}
.venv/bin/pip install -r requirements.txt
.venv/bin/python main.py
\end{verbatim}

\subsection*{Eigenst\"andige Pakete}
Mit \textbf{PyInstaller} werden gebündelte Pakete erzeugt, die alle Bibliotheken
enthalten:

\begin{verbatim}
.venv/bin/pip install pyinstaller

# macOS (Apple Silicon)  -> dist/IHKNachweise.dmg
bash packaging/build_macos.sh

# Windows 11             -> dist/IHKNachweise/IHKNachweise.exe
packaging\build_windows.bat
\end{verbatim}

\noindent
Das App-Icon (\texttt{packaging/icon.svg}) wird \"uber
\texttt{packaging/make\_icons.py} in \texttt{.icns} (macOS) und \texttt{.ico}
(Windows) umgewandelt und vom Build automatisch eingebunden. Ein
GitHub-Actions-Workflow (\texttt{.github/workflows/release.yml}) baut beide
Plattformen, sobald ein Tag \texttt{v*} gepusht wird.

\section{Speicherorte / Pfade}

Die Anwendung ist \textbf{portabel}: Alle Daten liegen in einem Ordner
\texttt{Daten} \emph{neben} der Anwendung. Es werden \textbf{keine
Administratorrechte} ben\"otigt und nichts in gesch\"utzte System- oder
Programmordner geschrieben. Die App darf in einem beliebigen, beschreibbaren
Ordner liegen (Home, Netzlaufwerk, USB-Stick) und wird manuell gestartet.

\begin{verbatim}
<frei gewaehlter Ordner>/
  IHKNachweise(.exe / .app)     # die Anwendung
  Daten/
    config.json                # Konfiguration
    modelle/                   # heruntergeladene GGUF-Modelle
    Nachweise/                 # erzeugte PDFs + Rohdaten (.txt)
\end{verbatim}

\noindent
Auf macOS wird bewusst \emph{neben} das \texttt{.app}-Bundle geschrieben (nicht
hinein), um dessen Signatur nicht zu verletzen. Im Entwicklungsbetrieb
(\texttt{python main.py}) entsteht \texttt{Daten/} in der Projektwurzel.

\medskip
\noindent
\textbf{Umleitbar:} \texttt{IHK\_DATA\_DIR} verlegt den gesamten Datenordner an
einen beliebigen Ort; \texttt{IHK\_MODELS\_DIR} und \texttt{IHK\_CONFIG\_DIR}
verlegen gezielt nur Modell- bzw.\ Konfigurationsordner.

\medskip
\noindent
\emph{Hinweis:} Beim Aktualisieren der App den Ordner \texttt{Daten} behalten --
er enth\"alt Modell, Konfiguration und alle Nachweise.

\section{Laufender Betrieb}

\begin{enumerate}
  \item \textbf{Metadaten} oben setzen: Name, Kalenderwoche (mit
        \"uberschreibbarem Datumsbereich -- wichtig bei
        Arbeitsbereichswechsel innerhalb einer Woche), Arbeitsbereich,
        Betreuer/in, Modell sowie Speicherort und Dateinamen-Muster.
  \item \textbf{Stichworte} der Woche links eintragen.
  \item \textbf{\glqq Erzeuge\grqq} klicken: Bei Bedarf wird das Modell geladen,
        anschlie\ss end strukturiert die LLM die Eingaben und das PDF erscheint
        rechts.
  \item \textbf{Ergebnis pr\"ufen.} Ist es unbefriedigend, erzwingt
        \glqq Neu generieren\grqq{} eine neue Fassung.
  \item \textbf{Ausgabe:} Pro Nachweis entstehen eine \texttt{.pdf} und eine
        gleichnamige \texttt{.txt} (Rohdaten). Die Fu\ss zeile des PDF nennt das
        verwendete Modell sowie die Erzeugungsdaten.
  \item \textbf{Sp\"ater fortsetzen:} \"Uber \glqq Rohdaten laden\grqq{} l\"asst
        sich eine \texttt{.txt} wieder einlesen und ein neues PDF erzeugen.
\end{enumerate}

\noindent
Die Metadaten (Name, Listen f\"ur Arbeitsbereiche/Betreuer, Pfade, Muster,
zuletzt gew\"ahltes Modell) werden in der Konfigurationsdatei gespeichert und
beim n\"achsten Start wiederhergestellt; sie lassen sich \"uber das
\glqq Datei\grqq-Men\"u zur\"ucksetzen.
